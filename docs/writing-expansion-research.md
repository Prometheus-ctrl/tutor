# 写作字数不足指导研究

更新时间：2026-10-27

目标：用户字数不够时，不再只说“补到 150 词”，而是告诉他**具体加什么内容**，且不跑题、不重复、不堆高级词。

## 现状

真实 2023 Part B：

- 当前约 99 词；
- 目标约 150 词；
- 批改只说“补到 150 词，先补题目要求的内容”；
- 用户知道要补，但不知道补哪一块。

## 核心原则

字数不够，通常不是“句子太短”，而是**内容单元不够**。

不要：

- 加形容词；
- 同义反复；
- 背高级句；
- 把一句话拆成三句。

要：

- 补一个数据点/对比；
- 补一个原因 + 具体例子；
- 补一句评论/建议/限制；
- 补题目要求但没写到的 bullet。

## 字数预算

### Part B（150 词）

```text
第一段 描述：约 40～50 词
第二段 原因：约 60～70 词
第三段 评论：约 35～45 词
```

### Part A（100 词）

```text
开头目的：约 20～25 词
主体两条 bullet：约 50～60 词
结尾：约 15～20 词
```

## 诊断：先数内容单元

### Part B

1. 图表主题/时间范围；
2. 最大项/起点；
3. 终点/变化；
4. 对比项/稳定项；
5. 原因一；
6. 原因一的例子/机制；
7. 原因二；
8. 评论/建议/限制。

缺哪一项，就补哪一项，不按“词数”硬凑。

### Part A

1. 称呼/目的；
2. 第一条 bullet；
3. 第二条 bullet；
4. 每条 bullet 的细节（谁/什么/何时/哪里/为什么/怎么做）；
5. 结尾/期待回复/落款。

## 输出格式

不要给完整范文。给 2～3 个“可加内容”，每个包含：

```text
加在哪：第二段原因后
加什么：一个具体原因 + 一个例子
预计增加：15～20 词
句首提示：One reason is that ...
```

用户自己决定加哪一个，自己写。

## 验证

### 真实 2023 B

- 当前 99 词；
- 目标 150；
- 找出缺的内容单元；
- 给出 3 个可加项，预计总增加 45～55 词；
- 检查是否和图表数据一致、是否跑题。

### 合成序列

- E1：只描述数据，没有原因；
- E2：有原因但没例子；
- E3：有原因但没评论；
- E4：Part A 只写了一条 bullet；
- E5：字数够但内容空泛（不应只加词）。

## 停止条件

- 输出格式稳定；
- 真实 2023 B + E1～E5 验证通过；
- 连续 3 次无新证据/无改动；
- 降为每周复盘。

## 不做

- 不替用户写完整段落；
- 不编造图表没有的数据；
- 不建议“为了字数”重复；
- 不把字数当成唯一质量指标。

## 2026-10-28 04:27

**问题**：字数不足时，如何从“补到 150 词”变成具体可加内容？

**实验/实现**：

- 检查真实 2023 B：当前约 96～99 词，目标 150；
- 实现 `writing_expansion.py`：按 Part A/B 诊断数据点、原因、例子、评论、bullet 细节；
- 接入 `review_writing` 的字数 must_fix action；
- 用真实 2023 B 跑批改。

**结果**：

- 2023 B 当前 96 词，需补约 54 词；
- 自动给出 3 个槽位：
  1. 第一段补中间年份/前后对比，约 +20 词；
  2. 第二段给原因补例子/机制，约 +20 词；
  3. 第三段补评论/限制/建议，约 +15 词；
- 合计约 +55 词，能覆盖缺口；
- 41 个测试通过。

**判断**：

- “补内容”已经能落到段落和功能，不再是空话；
- 数据点判断只看百分比，不把年份误当数据；
- 下一步验证 E1～E5，确认建议不重复、不跑题、不编数据。

**改动**：

- 新增 `writing_expansion.py`；
- 字数 must_fix 的 action 改为具体槽位；
- 新增测试。

**下一次**：

- 用 E1～E5 验证：只描述/没原因/没例子/没评论/Part A 漏 bullet。

## 2026-10-28 10:27

**问题**：扩写槽位在 E1～E4 场景下是否具体、不重复、不跑题？

**实验/结果**：

- E1 只描述：输出“补原因 + 补例子 + 补评论”，约 +60 词；
- E2 有原因没例子：第一个槽位就是“补具体例子”；
- E3 原因/例子/评论都有：不重复同一槽位，只补对比/限制；
- E4 Part A 漏 bullet：输出三条主体/结尾槽位；
- E5 字数已达标：不触发扩写建议，不硬加词；
- 真实 2023 B：槽位改为“例子 + 评论 + 数据对比”，合计约 +55 词；
- 50 个测试通过。

**判断**：

- 扩写建议从“补到 150 词”变成“加在哪、加什么、约多少词、句首提示”；
- 只描述内容不会先让加数据，而是先补原因/例子；
- 已完整的稿不会重复建议同一个槽位。

**改动**：

- 调整 `writing_expansion` 槽位顺序：原因 → 例子 → 评论 → 数据对比；
- 新增 E1～E4 回归测试。

**下一次**：

- 在真实写作页看 `must_fix.action` 的显示是否过长；
- 如果太长，把 action 缩成 2 个槽位 + “再加一个数据点”。

## 2026-10-28 16:27

**问题**：扩写 action 在写作页会不会太长、重复、难读？

**实验/结果**：

- 桌面：action 约 192 字符，`.next` 高约 80px，文字完整；
- 手机 390 宽：`.next` 约 174px，页面无横向溢出；
- 发现 UI 会把 `next_action` 再拼一次“这次只改：”，可能与 action 重复；
- 改成：同一个 action 只显示一次，`可加：` 后面的槽位拆成项目符号。

**判断**：

- 192 字符本身可接受，但一坨分号不适合手机；
- 拆成 3 条后能直接看到“第二段/第三段/第一段”；
- 不改变后端内容，只改展示。

**改动**：

- `writing.js` 增加 `actionHtml`；
- `.next` 不再重复前缀；
- `writing.html` 增加 `.action-list` 样式。

**下一次**：

- 用真实 AI 批改再确认 action 和槽位显示；
- 如果 action 超过 4 个槽位，缩成 2 个 + 一句补充。

## 2026-10-28 17:27

**问题**：真实 AI 批改下，扩写 action 会不会重复？

**实验/结果**：

- 真实 2023 B 仍是 1 条字数 must_fix；
- action 仍给 3 个槽位：例子 + 评论 + 数据对比，合计约 +55 词；
- 发现两个槽位都用 `For example` 开头，学生连写两段会重复；
- 改成：
  - 例子：`For instance, ...`
  - 数据：`In 20xx, the figure was ...`
  - 评论：`In my view, ...`

**判断**：

- 内容不重复，句子开头也不重复；
- 真实 AI 没有额外加 must_fix，字数仍由确定性规则兜底；
- 52 个测试通过。

**改动**：

- `writing_expansion.py` 槽位句首去重。

**下一次**：

- 等用户真的按槽位改一次，再判断 action 是否够用。
