# 写作修改过程学习报告研究

更新时间：2026-10-27

目标：把用户从初稿 → 批改 → 修改 → 定稿的过程，变成一份**有证据、能指导下一次写作**的学习报告。  
不是打分报告，不是“AI 判断你掌握了”，也不替用户写作文。

## 现有数据

`tutor/data/app.db` 的 `writing_tasks`：

- `first_draft`：第一次保存的稿；
- `draft`：当前稿；
- `feedback`：最近一次批改 JSON（`must_fix` / `optional` / `scores`）；
- `rewrite`：定稿时保存的重写稿；
- `final_at` / `feedback_at` / `rewrite_at`：时间；
- `status`：draft / feedback / ready / final。

缺口：

- 没有每次修改的完整快照，只有“初稿”和“当前/定稿”；
- 同一篇多次批改会覆盖 `feedback`；
- 无法还原“第 1 次改了什么、第 2 次又改了什么”。

## 要研究的问题

1. 报告最小结构是什么？必须能回答：
   - 改了什么？
   - 为什么改？
   - 改后问题解决了吗？
   - 同类问题以前出现过吗？
   - 下一次只练什么？
2. 需要不需要新增 `writing_revisions` 表，记录每次保存/批改的稿和 must_fix？
3. 没有多次快照时，能否只用 `first_draft` vs `final` 生成有限报告？
4. 报告如何避免变成“AI 评分/掌握判断”？
5. 报告如何避免太长，用户只看三件事就能行动？
6. 如何验证报告真的有用，而不是看起来漂亮？

## 报告草案结构

```text
1. 这次改了什么
   - 引用初稿句 → 定稿句
   - 只列 1～3 个实质变化

2. 为什么改
   - 对应 must_fix：数据错 / 任务漏 / 逻辑断 / 读不懂 / 语法
   - 没对应 must_fix 的变化标为“自主修改”

3. 改后是否解决
   - 同一 must_fix 是否消失
   - 是否引入新 must_fix
   - 不判断“掌握”

4. 重复模式
   - 同类硬伤在最近 N 篇出现几次
   - 只报事实，不下结论

5. 下一次只练什么
   - 一个功能/一个检查动作
   - 给一道换题迁移任务，不要求重写全文
```

## 验证方式

### 合成修改序列

只用于测试，不写入用户 `writing_tasks`：

- S1：初稿缺 advice → 批改 must_fix → 补 advice → 定稿；
- S2：初稿图表数据错 → 改数字 → 定稿；
- S3：初稿逻辑断 → 加过渡 → 定稿；
- S4：初稿语法错 → 改语法 → 定稿；
- S5：初稿干净 → 只有 optional → 直接定稿。

验证报告能否：

- 找到真正修改的那一处；
- 不把 optional 润色说成必须改；
- 不虚构未发生的修改；
- 给出一个可执行的 next practice。

### 真实数据

等用户真实写作后，用真实 `first_draft` / `feedback` / `final` 验证。没有真实数据时不伪造“用户进步”。

## 停止条件

- 报告 schema 稳定；
- 5 个合成序列验证通过；
- 连续 3 次无新证据/无代码改动；
- 降为每周复盘，或等真实稿再启动。

## 不做

- 不自动给“写作能力评分”；
- 不自动判断“已掌握”；
- 不生成范文；
- 不把报告写进用户草稿；
- 不为报告虚构修改历史。

## 2026-10-27 21:39

**问题**：只用现有 `first_draft` + 当前稿 + feedback，能生成什么程度的报告？

**实验**：

- 发现真实数据：`w:english2:2023:B` 初稿 27 词/3 句，当前稿 99 词/7 句；
- 实现 `tutor/server/writing_report.py` 原型；
- 生成报告到 `tutor/data/writing-report-sample.md`。

**结果**：

报告能给出：

- 初稿 → 当前稿词数/句数；
- 具体替换句；
- 对应 must_fix；
- 字数仍未达标；
- 下一次只补内容到 150 词。

报告不能给出：

- 中间改了几轮、每轮改了什么；
- 哪个 must_fix 是在第几次修改解决的；
- 同类问题是否跨篇重复。

**判断**：

- 现有数据只能做“初稿 vs 当前稿”的有限报告；
- 要支持“修改过程报告”，必须新增 `writing_revisions` 快照；
- 报告结构方向可用，但 diff 还需更细，避免只列长句。

**改动**：

- 新增 `writing_report.py` 原型；
- `writing-report-research.md` 记录本轮结论。

**下一次**：

- 设计并实现 `writing_revisions` 表：save/feedback/final 各存一次快照；
- 用真实 2023 B 和 S1～S5 合成序列验证报告；
- 不修改用户现有草稿。

## 2026-10-27 21:44

**问题**：如何保留“每一次修改”的历史，让报告能还原过程？

**实验/实现**：

- 新增 `writing_revisions(id,writing_id,kind,draft,feedback,created_at)`；
- `writing_save` 写 `save` 快照；
- `writing_feedback` 写 `feedback` 快照（含批改 JSON）；
- `writing_final` 写 `final` 快照；
- 用临时任务保存两次 + 定稿，验证快照顺序。

**结果**：

- 快照顺序：save → save → final；
- 最终快照保留 final 版本；
- 36 个测试通过；
- 用户现有草稿未被改写。

**判断**：

- 以后新写作可以还原“每次保存/批改/定稿”；
- 2023 B 的历史发生在新表之前，只能做“初稿 vs 当前稿”的有限报告；
- 报告原型下一步应优先读 `writing_revisions`，没有时才退回 first/current。

**改动**：

- `writing_revisions` 表；
- 三个写入点；
- `test_writing_revisions.py`。

**下一次**：

- 让 `writing_report.py` 读取 revisions，生成带时间线的报告；
- 用 S1～S5 合成快照验证“改了什么、解决没有、下一次练什么”。

## 2026-10-27 21:55

**问题**：S1～S5 五类修改序列，报告能不能正确说清“改了什么、解决没有”？

**实验**：

- S1 缺 advice；
- S2 图表数据错；
- S3 逻辑断；
- S4 语法错；
- S5 干净稿，只有 optional。

**结果**：

- 5 个序列都能生成时间线、修改句、must_fix、下一步；
- S1 发现一个关键问题：旧句“以后再说”仍在，但 advice 已补；报告原先会误判“原句还在=没解决”；
- 已改成“缺失类问题：当前稿新增 X 词，请对照题目确认”，不自动判掌握；
- 39 个测试通过。

**判断**：

- 报告不能只用“quote 是否还在”判断任务缺失类问题；
- 数据/逻辑/语法类可以用 quote 是否存在辅助判断；
- 缺失类必须看“新增内容 + 人工对照”，报告只能提示，不能下结论。

**改动**：

- 报告增加缺失类分支；
- 新增 S1 回归测试。

**下一次**：

- 给报告加一个只读 API/页面入口，让用户能在写作页点“看修改报告”；
- 没有真实稿时用 S1～S5 继续验证，不改用户数据。
